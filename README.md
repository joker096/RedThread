# НИТЬ — прототип серьёзных знакомств

Веб-прототип приложения для знакомств с намерением построить долгосрочные отношения или семью. Интерфейс адаптирован для мобильных экранов и desktop.

## Статус

**Сейчас это UI-прототип, а не production-сервис.** Анкеты, часть переписок, проверки безопасности, бонусные просмотры рекламы и Premium-переключатель используют демонстрационные данные.

Не показывайте demo-профили как реальных людей и не используйте демонстрационные статусы как доказательство личности.

### Реализовано в прототипе
- карточки демонстрационных анкет и фильтрация кандидатов по полу, стране, городу, намерениям и оценке совместимости;
- ориентировочная совместимость по ответам, интересам и целям;
- демонстрационные чаты и приглашения на встречу;
- демонстрационные состояния Lady Premium и рекламного менеджера;
- эвристическая проверка текста анкеты на отдельные спам-маркеры;
- адаптивный интерфейс.

### Не подключено
- регистрация и вход с настоящей проверкой личности;
- постоянная база данных и серверное хранение анкет, лайков, совпадений и сообщений;
- real-time доставка сообщений и уведомления;
- платежи и подтверждение статуса Premium;
- рекламный провайдер и достоверная статистика показов/дохода;
- биометрическая проверка, настоящая антифрод-система и очередь модерации;
- юридические документы, политика конфиденциальности и процедуры удаления данных.

Индекс совместимости — ориентир для начала разговора, не психологический диагноз и не научный прогноз успеха отношений.

## Запуск локально

Требуется Node.js 22 или совместимая актуальная версия.

```bash
npm install
npm run dev
```

Vite запускает интерфейс на порту 3000.

## Серверный каркас (начальный этап)

Выбран базовый стек для следующего этапа: **Node.js 22 + Express + PostgreSQL**. В репозитории добавлены Express API, health/readiness endpoints, PostgreSQL-миграции для аккаунтов, анкет, предпочтений локации, лайков, взаимных совпадений, сообщений, партнёров, проверки документов, заявок на услуги, жалоб и серверных сессий. Реализованы регистрация/вход по email, выход, проверка текущей сессии, хеширование паролей через scrypt, cookie HttpOnly/SameSite=Lax, проверка Origin, лимит попыток входа и тесты auth-сценариев. Защищённые endpoints включают `GET /api/profiles/search` и `GET/PATCH /api/profiles/me`, постановку и отмену лайка, создание совпадения только при взаимной симпатии, список совпадений, чтение/отправку сообщений только участниками активного совпадения и отправку жалоб. Поиск выбирает анкеты противоположного пола среди активных пользователей, фильтрует по стране, городу и цели отношений и возвращает возраст вместо даты рождения.

### Локальный запуск API

1. Скопируйте `.env.example` в `.env` и укажите параметры своей PostgreSQL-базы в `DATABASE_URL`.
2. Установите зависимости: `npm install`.
3. Примените миграции: `npm run db:migrate`.
4. В отдельном терминале запустите API: `npm run dev:api`.
5. Запустите frontend: `npm run dev`. Vite проксирует запросы `/api` на API-порт 3001.

Проверка доступности API: `GET /api/health`. Проверка соединения с базой: `GET /api/ready`; без настроенной базы она намеренно возвращает HTTP 503. Поиск анкет требует активной сессии: `GET /api/profiles/search?country=Грузия&city=Тбилиси` (также поддерживаются `intent`, `limit` до 50 и `offset`). Для регистрации нужны email, пароль длиной 12–128 символов, дата рождения 18+, пол, страна и город.

**Ограничения:** это начальный backend, а не готовый production-сервис. Реализована базовая регистрация/авторизация, но ещё не реализованы восстановление пароля, подтверждение email, управление активными сессиями, CRUD API, серверная проверка доступа к совпадениям/чатам/заявкам, загрузка документов и платежи. Не используйте API в production и не загружайте реальные документы, пока не будут завершены оставшиеся меры защиты, аудит и безопасное хранилище. Текущий rate limiter хранит счётчики в памяти одного процесса; для нескольких экземпляров нужен общий store (например, Redis). Таблица документов содержит только приватный ключ объекта и метаданные, а не содержимое файлов.

## Партнёрские услуги после взаимной совместимости

В интерфейс добавлен демонстрационный каталог внутри чата пары: семейные юристы и адвокаты, аренда свадебных платьев, фотографы/видеографы, ведущие, площадки и специалисты по свадебному образу. Есть свободный поиск по стране и городу, форма-заготовка поставщика и описание возможной модели монетизации. Все карточки явно помечены как демонстрационные: это не реальные рекомендации, цены и бронирования не подключены, заявка не отправляется.

### Проверка юридических специалистов перед публикацией

- Проверить личность специалиста и полномочия представителя организации.
- Проверить юридическое образование и действительность диплома.
- Проверить лицензию, членство в палате или статус адвоката, если это предусмотрено законом выбранной страны.
- Сверить номер с официальным государственным или профессиональным реестром.
- Зафиксировать юрисдикцию, регион и конкретные виды услуг, на которые специалист имеет право; предусмотреть периодическую повторную проверку.
- Хранить документы в закрытом хранилище с ограничением доступа и журналом действий; не публиковать сканы удостоверений.
- По брачным договорам учитывать страну применимого права и место заключения брака; до заказа раскрывать цену, объём услуги, сроки и условия возврата.

### Коммерческая модель поставщиков

Возможные модели: платная подписка поставщика, комиссия с завершённого заказа и отдельно маркируемое продвижение. Оплата за продвижение не должна влиять на статус проверки квалификации. Для production нужны серверный каталог, ручная проверка документов, платежи, договоры, возвраты, жалобы и юридическая проверка требований каждой страны.

## Следующие этапы до production

1. Развернуть PostgreSQL и применить начальную миграцию из серверного каркаса.
2. Реализовать регистрацию, безопасное хеширование паролей, сессии и серверную авторизацию.
3. Подключить frontend к серверной авторизации, поиску, лайкам, совпадениям и сообщениям; добавить восстановление пароля и подтверждение email.
4. Подключить платежи с проверкой webhook и учёт подписки Premium на сервере.
5. Подключить реальный рекламный SDK и считать доход только по подтверждённым событиям провайдера.
6. Подключить проверку личности у специализированного провайдера; не хранить документы/биометрические данные без необходимости.
7. Добавить rate limiting, защиту от спама, аудит безопасности, политику приватности и удаление аккаунта.
8. Проверить сценарии e2e на мобильных устройствах и провести тестовую публикацию.

## Переменные окружения

Текущий frontend не требует собственных секретов. Никогда не помещайте ключи платёжного, рекламного или identity-провайдера в код браузера. Серверные секреты должны храниться в окружении хостинга, а не в репозитории.
