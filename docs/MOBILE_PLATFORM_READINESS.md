# Vow Mobile Platform Readiness

Status: mobile foundation implemented; backend auth, native client transport, Android/iOS cloud builds and CI regression gates are in place. Real-device and production-release blockers remain.
Target platforms: Android and iOS only.
Implementation: preserve the React UI, package it with Capacitor, and keep Express/PostgreSQL as the shared backend.

## Confirmed repository state

- The dedicated branch is `feat/mobile-capacitor-foundation`; its baseline is the current `main` commit `d57b7fa624871ed8a3e3ed99494701d95f976258`.
- The client is React 19 + TypeScript + Vite; the backend is Express + PostgreSQL.
- Capacitor 8.6.0 is installed. Android and iOS projects are generated by the platform ensure scripts in clean local/CI environments.
- The provisional app identifier is `com.vow.app`; it must be confirmed before store submission.
- The native client stores refresh tokens through the secure-storage plugin (Keychain / Android Keystore-backed storage) and keeps access tokens in memory.
- Native API transport uses `VITE_API_BASE_URL`, requires HTTPS in production, refreshes sessions with a single-flight guard and sends bearer tokens without browser cookies.
- The server supports native registration, email verification, login, refresh rotation/replay detection, logout, logout-all and password-reset flows.
- Browser cookie authentication remains separate. Browser Origin/CSRF checks are not replaced by the native bearer path.
- The branch has CI, Browser E2E, Android debug APK and iOS Simulator build workflows. These are compile/regression checks, not store-signed releases.

## Completed foundation

### Authentication and API transport

- Migration `212_mobile_sessions.sql` adds device-scoped sessions and append-only consumed refresh-token history.
- Opaque 256-bit access/refresh tokens are stored only as SHA-256 hashes.
- Access lifetime is 10 minutes; refresh lifetime is an absolute 30 days.
- Refresh rotation is transactional. Reuse of a consumed refresh token revokes all mobile sessions for that account.
- Native access tokens are accepted by shared protected API routes; browser sessions continue to use the HttpOnly `nit_session` cookie.
- Native CORS is allowlisted for Capacitor origins and configured additional origins; credentialed CORS is not enabled.
- Password reset, account suspension and account deletion invalidate mobile sessions.
- The client uses secure refresh-token storage, in-memory access tokens, a single-flight refresh operation and a native API base URL.
- Native login/registration and recovery flows are wired into the existing account UI. Google browser sign-in and Paddle checkout are intentionally hidden in native builds until native provider sign-in and store-compliant billing are implemented.

### Verification

- The full CI workflow runs migrations, lint, the complete test suite, build and container checks.
- Browser E2E remains a required regression gate even though Vow is not planned as a public web product.
- The mobile build workflow compiles an unsigned Android debug APK and an iOS Simulator app on hosted runners.
- Require CI and Browser E2E to pass on the exact same branch HEAD before considering the work verified. Require mobile platform builds on the current mobile-source HEAD before treating a native build as validated.

## Remaining release blockers

### 1. API hostname, TLS and real-device connectivity

No Vow production API hostname has been selected. A public HTTPS hostname and valid TLS certificate are required before a real-device release candidate can connect to the production backend. Do not put API secrets in `VITE_*` variables; `VITE_API_BASE_URL` is a public URL.

### 2. Android and iOS device validation

- Android debug APK builds in CI; local Android development is supported on Windows with Android Studio and an emulator.
- iOS Simulator builds in hosted macOS CI; a local Mac is not required for this workflow.
- Physical-device validation, signed release builds, App Store Connect/TestFlight and Google Play internal testing still require the relevant developer accounts, signing/provisioning configuration and a reachable HTTPS API.

### 3. Camera, microphone, location and verification media

The API currently sends `Permissions-Policy: camera=(), microphone=(), geolocation=()`. This intentionally blocks browser media APIs. Before enabling media capture, map the actual flows and use native Capacitor plugins with narrowly scoped permission prompts. Preserve server-side upload validation and identity-verification checks. Do not request permissions at app launch.

### 4. Native providers and deep links

- Google sign-in currently uses browser Google Identity Services and is hidden in native builds. Native provider SDK sign-in and server-side ID-token exchange remain to be implemented.
- Email verification and password-reset query links need verified HTTPS app links / iOS Universal Links with safe browser fallback.
- Didit verification return/deep-link behavior needs a native flow without weakening webhook signature checks.

### 5. Billing and store policy

The backend remains Paddle-only. Paddle checkout is hidden in native builds pending a reviewed Google Play / App Store compliant approach for digital subscriptions. Do not silently add Stripe or switch billing providers. Live billing remains disabled until the decision is made.

### 6. Push notifications and app lifecycle

Native push registration, permission UX, token rotation, notification routing and deep-link handling are not yet implemented or physically tested.

## Deployment target

Vow is a mobile product, not a public website/web product. The production VPS should run the API, PostgreSQL, migrations and required background workers behind a TLS reverse proxy. Do not deploy the Vow Nginx frontend as a public product. Do not deploy until the API hostname, TLS, secrets, private storage, backups, monitoring and operational checks are ready.

## Delivery sequence

1. Backend native authentication and browser compatibility — implemented and covered by integration tests.
2. Capacitor client, secure token storage, API transport and native account UI — implemented.
3. Android debug and iOS Simulator cloud builds — implemented and build-checked.
4. Finish edge-case auth/security regression checks and keep CI + Browser E2E green on the same HEAD.
5. Validate Android emulator and physical Android/iOS devices against a configured HTTPS API.
6. Implement native Google sign-in, app/universal links, Didit return flows, camera/microphone/location and push notifications with corresponding tests.
7. Resolve store billing, app identifiers, signing and privacy disclosures; prepare signed store builds only after release blockers are cleared.

## Scope and safety boundaries

- No public Vow website or web product is planned. Browser code remains a development and regression surface.
- Keep this work on `feat/mobile-capacitor-foundation`; do not modify `main`, merge, or create a PR until the feature branch is fully audited and the user authorizes the next step.
- Successful CI or simulator packaging does not mean the app is production-ready.


## Deep links implementation status

- Implemented the Capacitor App plugin listener for foreground and cold-start links.
- Implemented strict URL parsing, a bounded cold-start queue, and duplicate suppression for one-time action tokens.
- Implemented native account handling for verified email and password-reset HTTPS app links, plus Trust Center refresh on Didit return.
- Registered `vow://identity/return` on Android and iOS. This custom scheme carries no token.
- Prepared optional verified HTTPS app-link configuration. Set repository variable `VOW_APP_LINK_HOST` only after choosing the production app/API hostname. The value must match the hostname in `APP_URL` / `APP_ORIGIN`.
- Still blocked: domain ownership/DNS, Android `assetlinks.json` signing fingerprint, Apple Team ID and `apple-app-site-association`, final app identifier, and real-device verification. Do not mark Universal Links/App Links production-ready before these are published and tested.

- Didit now opens in Capacitor's native browser surface. On iOS the presented browser is closed after the verified callback returns; on Android the app leaves the Custom Tab lifecycle alone.

## Notifications and media follow-up

- In-app notifications remain database-backed. Native app resume now triggers a refresh of notification rows/unread counts and Trust Center state; this is not remote push delivery.
- Remote push is intentionally not enabled. Firebase/FCM, Apple APNs credentials, final application identifiers, encrypted token storage, provider workers and physical-device tests are prerequisites. See `docs/MOBILE_PUSH_READINESS.md`.
- Native camera/microphone capture is intentionally not enabled. The global browser Permissions-Policy remains restrictive, and L3 remains disabled until production encrypted storage, key management, backup and purge monitoring are ready. A native recording implementation must include deterministic local-file cleanup and server-authoritative media validation. See `docs/MOBILE_MEDIA_READINESS.md`.
