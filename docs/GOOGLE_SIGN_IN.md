# Вход и регистрация через Google

Vow использует Google Identity Services (GIS) только при заданном серверном GOOGLE_CLIENT_ID. Используйте OAuth 2.0 client ID типа **Web application** и внесите точные production/dev origins в Authorized JavaScript origins. OAuth client secret не нужен и не должен попадать в приложение.

## Последовательность входа

1. Frontend запрашивает у API одноразовый challenge. API генерирует криптографически случайный nonce, хранит только его хеш и задаёт TTL 5 минут.
2. Frontend передаёт nonce в GIS initialize. GIS возвращает подписанный ID token, в котором nonce должен совпадать.
3. API проверяет токен библиотекой google-auth-library: подпись, issuer, audience, authorized party (`azp`, если он обязателен или присутствует), временные claims, nonce и подтверждение email. Для токена с несколькими audiences обязателен `azp`, совпадающий с Vow client ID. Затем API атомарно погашает challenge; повторное использование отклоняется.
4. Если Google subject уже связан с активной Vow-учётной записью, API создаёт обычную Vow-сессию.
5. Для новой учётной записи API выдаёт отдельный случайный регистрационный билет с TTL 10 минут. Хранится только хеш. Билет привязан к Google subject и подтверждённому email.
6. Пользователь завершает обязательную анкету и задаёт пароль. Билет удаляется под блокировкой строки в той же транзакции, что создание пользователя, профиля, Google identity и сессии. При откате транзакции билет остаётся пригодным; после успешной регистрации его временные email/subject-данные удаляются. Повторное использование и истёкший билет отклоняются.
7. Неиспользованные challenge/ticket rows удаляются фоновым таймером API не реже чем раз в 15 минут после истечения TTL; успешная регистрация удаляет билет сразу.

## Правила привязки аккаунта

- Совпадение email с локальной учётной записью не приводит к автоматическому объединению. Пользователь должен войти исходным способом.
- Изменение email в Google не меняет email Vow автоматически.
- Google subject является стабильным внешним идентификатором; email не используется как ключ Google identity.
- При переходе аккаунта в состояние deleted Google subject удаляется отдельным DB-триггером в той же транзакции. Это важно, потому что обычное удаление Vow — soft tombstone, а не физический DELETE.
- При отключённом GOOGLE_CLIENT_ID конфигурация сообщает configured: false, а challenge и sign-in endpoints завершаются fail-closed с HTTP 503.

## Настройка

### Локальная проверка без домена и хостинга

Для разработки публичный домен, хостинг и HTTPS не нужны. Vow по умолчанию использует Vite на `http://localhost:3000`, API на порту `3001` и `APP_ORIGIN=http://localhost:3000`.

1. Создайте в Google Cloud Console OAuth client типа **Web application**.
2. В **Authorized JavaScript origins** добавьте ровно `http://localhost:3000`. Если открываете Vow на другом имени или порту, добавьте именно этот origin и установите такое же значение в `APP_ORIGIN` API.
3. Скопируйте только Client ID в `GOOGLE_CLIENT_ID` локального API `.env`; не добавляйте client secret и не используйте префикс `VITE_`.
4. Перезапустите API и откройте приложение именно через `http://localhost:3000`, затем проверьте popup-вход и регистрацию.
5. Для GIS popup flow отдельный redirect URI не требуется. Google client ID публичен; секреты остаются только на сервере.

### Перед публичным запуском

1. Добавьте точные production HTTPS origins в Authorized JavaScript origins.
2. Настройте HTTPS и отдельный staging OAuth client/окружение.
3. Проверьте реальные токены и popup flow в staging до включения Google-входа на production.

Не включайте Google-вход в production, пока не пройдены миграции 210 и 211, интеграционные тесты, CI и Browser E2E на одном и том же commit SHA. Политика конфиденциальности должна быть заполнена и юридически проверена до публичного запуска.
