## 2. Latest work in this session

### 2.1. Didit L2 SQL NULL bypass — fixed

Migration 116 added a PostgreSQL CHECK constraint for verified Didit state. PostgreSQL CHECK accepts both TRUE and UNKNOWN; because `provider_status` is nullable, a row with `status='verified'`, live environment, a session ID, and NULL provider status could satisfy the constraint as UNKNOWN.

Changes:
- Added `server/migrations/117_didit_verified_state_check_null_safe.sql`.
- Migration 117 replaces the constraint and wraps the verified-evidence predicate in `IS TRUE`.
- Added `server/diditVerifiedStateSchema.integration.test.js` coverage that clones the production table constraints, confirms a valid Approved/live/session row is accepted, and confirms a NULL provider verdict is rejected with SQLSTATE `23514`.
- Added the integration test to the explicit `npm test` script in `package.json`.

### 2.2. L3 encrypted media — authenticate before exposing plaintext

The previous AES-256-GCM read path streamed decipher output before final tag verification. That could expose unauthenticated plaintext to a future HTTP playback consumer if ciphertext were tampered with.

Changes:
- `server/identityL3Storage.js` now reads a size-bounded encrypted object, validates its structure, verifies the complete GCM tag, and only then returns a readable plaintext stream.
- Wrong-key and ciphertext-tampering tests now assert that opening the object itself rejects before a plaintext stream is returned.
- The storage primitive remains unused by production HTTP routes; this fix does not make L3 operational.

## 5. Confirmed incomplete features / release gates

### P0 — L3 is not an operational workflow

At the handoff HEAD, `server/index.js` exposes:

- `GET /api/trust/summary`

It does **not** expose L3 upload-token, video-upload, upload-completion, moderator-queue, moderator-playback, approval/rejection, revocation, or expiry-worker routes. Existing admin routes cover screenings, reports, photos and audit logs, not L3 video moderation.

Existing helpers:
- `server/identityL3Storage.js`
- `server/identityL3UploadTokens.js`
- migrations 114–117 and corresponding tests

These helpers are foundations only. Do not call the feature complete and do not bypass the male L2+L3 gate.

Required before L3 can be enabled:
1. Dedicated private media storage configuration; do not reuse `PHOTO_STORAGE_DIR` or public photo volume.
2. Managed/envelope key strategy and documented key rotation/recovery. Do not claim unlinking a file on SSD/backups is secure erasure.
3. Authenticated, single-use, short-lived upload endpoint that consumes the token before accepting bytes and holds the account-safety transaction/lock until the encrypted object key is persisted.
4. Strict byte, MIME, container, codec, duration (30–60 sec), resolution and parser limits.
5. Isolated media parsing/scanning pipeline; no submission enters `pending_review` until object existence, checksum and scan/metadata checks succeed.
6. Moderator queue and playback with active admin/moderator authorization, no self-review, row locks, short-lived audited access, and no storage key/public URL exposure.
7. Transactional approve/reject/revoke, immutable audit history, six-month expiry enforcement and an operational expiry worker.
8. Physical object deletion/retention job integrated with withdrawal, rejection, expiry, revocation and account deletion; deletion must not erase DB references before object cleanup is confirmed.
9. PostgreSQL, concurrency, API and Browser E2E coverage for all transitions, cross-account access, replay, expired token, wrong-user object, upload interruption, scanner failure, concurrent decisions, expiry and deletion.
10. Enable only behind a server-side feature flag after storage health checks and security review. Until then keep the gate fail-closed.
