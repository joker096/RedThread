# Vow Mobile Development

Vow's product targets are Android and iOS. The existing browser build remains a development/regression surface only; it is not a planned public web product.

## Current foundation

- Capacitor 8.6.0; \`com.vow.app\` is a provisional application identifier. Confirm the final reverse-DNS identifier before any store submission.
- \`@aparajita/capacitor-secure-storage\` 8.0.1 stores refresh credentials in the native secure store. Access tokens remain in memory.
- The shared Express API accepts native bearer sessions on protected routes. Browser cookie sessions remain separate.
- Native requests require \`VITE_API_BASE_URL\`. Production builds require HTTPS.
- Android/iOS platform directories are generated with the \`cap:ensure:*\` commands. They are not generated by a normal web build.

## Windows: Android emulator

Requirements: Node.js 22, Android Studio 2025.2.1 or newer, and an Android SDK platform (API 24 or newer). Android Studio installs/manages the appropriate JDK.

In PowerShell, from the repository root:

\`\`\`powershell
npm install
npm run cap:ensure:android

# Android emulator -> Windows host API on port 3001.
$env:VITE_API_BASE_URL = "http://10.0.2.2:3001"
$env:VITE_ALLOW_INSECURE_API = "true"
$env:VOW_ALLOW_INSECURE_MOBILE_DEV = "true"

npm run cap:sync:android:dev
npm run cap:open:android
\`\`\`

Start the local Vow API and its required PostgreSQL/migration services on the Windows host before testing. The emulator address \`10.0.2.2\` routes to the host machine. For a physical Android device, use the host's LAN IP and allow the development port through the local firewall.

The two insecure-development flags are deliberately required for local HTTP testing. They enable Android cleartext/mixed-content only in the generated development configuration. Never set either flag for a release build.

## Android release build

A release build must use a real HTTPS API origin and must not enable insecure development flags:

\`\`\`powershell
$env:VITE_API_BASE_URL = "https://YOUR-API-HOST"
Remove-Item Env:VITE_ALLOW_INSECURE_API -ErrorAction SilentlyContinue
Remove-Item Env:VOW_ALLOW_INSECURE_MOBILE_DEV -ErrorAction SilentlyContinue

npm run cap:sync:android
npm run cap:open:android
\`\`\`

Use Android Studio to create a signed release bundle only after the app identifier, signing key, API hostname, TLS, privacy disclosures and store policy decisions are final.

## iOS

A local Mac is not required for the planned workflow. iOS platform generation/building is handled on a hosted macOS runner with Xcode. For a local Mac, the equivalent setup is:

\`\`\`bash
npm install
npm run cap:ensure:ios
export VITE_API_BASE_URL="https://YOUR-API-HOST"
npm run cap:sync:ios
npm run cap:open:ios
\`\`\`

iOS testing must use an HTTPS API origin. The Android-only HTTP development exception does not relax iOS App Transport Security.

## Cloud platform build artifacts

The `Mobile platform builds` GitHub Actions workflow generates native platform projects in clean runners and builds:
- an unsigned Android debug APK;
- an iOS Simulator .app bundle.

The artifacts are retained for 14 days and are available under the workflow run's Artifacts section. These are compile/smoke-test outputs, not store-signed release packages. The workflow does not set a Vow API hostname, so the artifacts are not connected to a production backend until a build is made with the correct `VITE_API_BASE_URL`.

## API hostname and release blocker

No Vow production API hostname has been selected yet. Until a public HTTPS API hostname and valid TLS certificate exist, a mobile package can be built for shell/emulator validation, but it cannot be considered a usable release candidate for real devices.

Do not put API secrets in \`.env\` variables prefixed with \`VITE_\`; Vite embeds those values into the client bundle. \`VITE_API_BASE_URL\` is a public URL, not a secret.

## Store and product constraints

- Google sign-in is temporarily hidden in native builds until native provider sign-in and server token exchange are implemented.
- Paddle checkout is not exposed in native builds pending a reviewed Google Play / App Store compliant subscription design. This does not change the backend's Paddle-only integration or authorize adding Stripe.
- Camera, microphone, push notifications, deep links and real-device verification flows are subsequent milestones, not yet release-ready.


## Verified app links and token safety

- Token-bearing verification and password-reset actions are accepted by the native app only from HTTPS URLs whose hostname exactly matches the build-time `VITE_APP_LINK_HOST`.
- Custom `vow://` links are restricted to the non-secret identity return marker. Account action tokens must never be placed in custom-scheme URLs.
- The existing HTTPS links from `accountActionUrl` remain the email source of truth. Android/iOS open them in the app only after domain association is configured and verified.
- The native build workflow uses repository variable `VOW_APP_LINK_HOST` for the native Android/iOS association and runtime host allowlist. It must match `APP_URL` / `APP_ORIGIN` and contain only a hostname.
- Publish Android `/.well-known/assetlinks.json` with the final application ID and signing-certificate SHA-256 fingerprint, and Apple `/.well-known/apple-app-site-association` with the final Team ID and bundle ID before enabling production app links.
- Didit callback uses `APP_ORIGIN/?identityVerification=return`; the app refreshes Trust Center only when that exact HTTPS host is associated. The custom scheme callback is not trusted to carry verification credentials.
